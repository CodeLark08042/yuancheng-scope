## 1. `DIG` 字节位序：已按正式 V1.1 统一（B 端已修正）

### 1.1 结论

**B 端已改为按正式协议 V1.1 第 3.1 节的 `bit0=D1 / bit1=D2 / bit2=D3` 解析，与 A 端现状一致。**

上一版清单里 B 端称"文档前后矛盾"，这个判断不准确——`CH_MASK`（通道开关）和 `DIG`（采样电平）
是两个独立字段，各自定义位序，文档本身是自洽的。A 端按文档实现，B 端才是偏离方，因此由 B 端修正。

双方对齐后的位定义：

| 字段 | 位定义 | 用途 |
|---|---|---|
| `CH_MASK` | `bit0=CH1, bit1=CH2, bit2=D1, bit3=D2, bit4=D3` | 通道是否开启 |
| `DIG`（每点第 5 字节） | `bit0=D1, bit1=D2, bit2=D3`，bit3~7 恒 0 | 该采样点三路数字电平 |

两者位位置不同，不可混用。

## 5. 触发约定

B 端已全部按下面实现（界面 + 下发 + 回执显示），触发算法在 A 板。请 A 逐条确认。

**基础 7 条**

1. 触发点固定在每帧第 0 个采样点（屏上每格左边缘），预触发深度 0
2. 检测到触发条件后，以该点为输出帧第 0 点，**输出帧从该点起连续取 50 点**；SEQ 照常递增

   > 更正上一版的说法：不需要的是**预触发历史缓存**（预触发深度 0，不用往回找触发点之前的点）；
   > 但**输出帧确实会跨采集块**。A 端用定时器 + DMA 固定 50 点一组采集，若触发点落在某组第 20 点，
   > 输出帧就是"本组 20~49"+"下一组 0~19"的拼接。
   > 因此实现上需要让**输出帧与采集块边界解耦**：用连续环形缓冲，触发命中后记下偏移指针，
   > 从该指针连续取 50 点（跨块时自动接上下一块），而不是把每次 DMA 完成的 50 点当成一帧发出去。
   > B 端只要求"第 0 点 = 触发点、连续 50 点、间隔符合档位"，不关心 A 内部怎么拼。

3. 触发电平 0~255 线性映射 0~VREF，阈值换算成 ADC 码比较（`th = level × 4095 / 255`）
4. 数字通道触发只看逻辑沿，忽略电平参数
5. 500ms 内无触发则自由运行
6. 状态帧发送时机：上电一次；收到 CMD 0x06 立即回；触发命令生效后回一次
7. 命令生效时机：下一帧起

**补充条款（V1.1 之后追加）**

8. `TRIG_SRC=0`（关闭）时 A 板不等待触发，立即自由运行，不适用第 5 条超时
9. 触发源通道被 CH_MASK 关闭时，A 板同样按自由运行处理，**不得停在"等待触发"**；
   状态帧仍原样回显当前触发配置；该通道重新打开且配置仍指向它时，自动恢复触发，B 不需重发命令
10. 状态帧对最近一次收到的 CMD 0x03/0x04/0x05 参数**逐字段原样回显**，
    包括数字触发源时"忽略"的 TRIG_LEVEL（仍回显最近一次收到的值，不得清零或改写）
11. 每帧第 0 点恒为触发点，自由运行时为窗口起点；B 端不区分"触发命中"与"自由运行"，
    帧内不另标触发位置；若以后要显示 TRIG'D/AUTO，必须新增协议字段
12. 阈值比较：`th = level × 4095 / 255`（整数截断）。**必须用"相邻两点跨越阈值"判定，
    不能只判当前点**（否则持续高电平期间会反复触发）：
    - 上升沿：前一点 `raw12 < th` 且当前点 `raw12 >= th`
    - 下降沿：前一点 `raw12 > th` 且当前点 `raw12 <= th`
    - 任意沿：相邻两点跨越 `th`（方向不限）
13. 数字"任意边沿"（mode=2）：相邻两采样点电平不同即算触发，不要求最小稳定时间

> 补正说明：上一版第 12 条只写了"上升沿 `raw12 >= th`"，仅比较当前点，判定不完整。
> 已按 A 端意见改为前后两点跨越式判定。

> 第 9 条尤其重要：不写死的话 A 可能一直等一个已被关闭的通道，B 端会看到链路 500ms 超时而误报断开。
> 第 10 条不遵守的话，B 端触发指示的绿色"已确认"框在数字源下不会亮（B 已做兼容，但建议按第 10 条实现）。

## 8. 建议的联调顺序

1. **10ms 档 + 仅 CH1**，UART 打通：B 屏出现稳定正弦/电位器波形，CRC 为 0、丢帧为 0
2. 加 CH2 → 加 D1/D2/D3 → 加 5ms 档
3. 加矩形波环回：A 的矩形波输出接到 A 的 CH1 输入（和一路数字输入），B 屏应同时看到方波；
   用 CMD 0x07 改频率，B 屏测量值应与设定值一致、状态帧回显一致
4. 加触发：先用 CH1 上升沿 + 固定电平，看 B 屏波形是否稳定不动
5. 最后切以太网 UDP，从 10ms 档开始逐档往上验证，记录实测帧率与丢帧

**关于 A 端"B 能否直接接收 `CH_MASK=0x1F`、暂时只显示 CH1"**

可以。B 端已加"本地显示掩码"与 A 端 `CH_MASK` 取交集：

```c
/* A 的 ch_mask 表示它采了哪些通道；本地 g_mask 表示用户想看哪些；两者取交集 */
static uint8_t cur_mask(void) {
  uint8_t m = proto_stat()->ch_mask;
  return m ? (uint8_t)(m & g_mask) : g_mask;
}
```

含义：

- A 一直发 `0x1F`（五通道全采）完全没问题，B 端照样解析，不丢帧、不报错
- 用户在 B 的顶栏点掉 CH2/D1/D2/D3，只是本地不再画那几路，**不会向 A 发 CMD 0x02**
  （A 未实现 0x02 接收期间，B 发出去也收不到回执，属于预期）
- 一旦 A 实现了 CMD 0x02 接收，B 的通道按钮会自动同时改 `g_mask` 与下发 `CMD_CHMASK`，
  届时两边掩码会同步；在 A 没实现之前，B 端本地过滤是唯一手段
- A 侧只有一个隐含要求：`CH_MASK` 必须如实反映**实际采到的通道**（现在恒发 `0x1F` 也符合），
  不要发一个和实际采样不符的掩码，否则 B 端会把该画的通道过滤掉
